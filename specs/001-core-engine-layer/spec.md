## Clarifications

### Session 2026-11-09

- Q: 8 类调整的参数应该用哪种统一的取值刻度约定？ → A: 全部调整统一采用 0.0–2.0 浮点因子刻度，1.0 为中性值（内部可映射到具体算法语义，但对外参数模式与序列化统一为此刻度）
- Q: RAW 支持的验收样片以哪种相机格式为主？ → A: 以 .ARW（索尼）为主验收格式；其余常见 RAW 格式尽力支持，解码失败走格式化异常路径
- Q: 交互级低分预览的单次重渲染应该以多长时间为验收上限？ → A: 不设硬性时间指标，仅验收「低分先行、无全图级阻塞」的顺序性
- Q: 参数文件（Sidecar）与原图的命名关联规则是什么？ → A: 同主名换扩展名：photo.jpg → photo.json（对应 Lightroom XMP Sidecar 惯例）

## User Scenarios & Testing *(mandatory)*

本特性的「用户」是两类角色：**上层应用开发者**（桥接层/未来 UI 的集成者）与**端到端使用者**（通过脚本或未来界面完成「打开 → 编辑 → 导出」的摄影师）。核心引擎层不提供任何图形界面，全部能力可在无浏览器的命令行环境独立验证。

### User Story 1 - 对图片应用基础调整并出图 (Priority: P1)

作为上层应用开发者，我向引擎提交一张图片与一组调整参数（如亮度 1.3、对比度 0.9），引擎按顺序应用调整并返回处理后的图像结果，使我无需了解任何界面框架即可完成一次完整的图像加工。

**Why this priority**: 这是引擎的存在理由——没有「应用调整并出图」，其余一切能力都无意义；对应里程碑 M1（继承体系一落地）。

**Independent Test**: 在命令行环境给定一张样例图与一组调整参数，运行引擎后得到输出图像文件；仅需本故事即可交付一个可用的最小图像处理引擎。

**Acceptance Scenarios**:

1. **Given** 一张有效 JPEG 图片，**When** 应用「亮度提升」调整，**Then** 输出图像的像素值整体变亮，原始文件字节保持不变
2. **Given** 一张有效图片，**When** 依次应用多个不同类型的调整（亮度、对比度、饱和度、锐度），**Then** 输出结果与逐条手工应用的结果一致（顺序执行）
3. **Given** 任一调整，**When** 以超出合法范围的参数调用，**Then** 引擎拒绝执行并报告明确的参数错误，不产生损坏的输出
4. **Given** 引擎全部代码，**When** 静态检查引擎源码是否引用任何界面框架，**Then** 结果为零引用

---

### User Story 2 - 非破坏性编辑会话与撤销/重做 (Priority: P1)

作为上层应用开发者，我通过编辑会话记录每一次调整操作；同一滑块的连续多次调整自动合并为一条记录；我可以撤销最近的操作并重做已撤销的操作，全过程不触碰原始像素。

**Why this priority**: 非破坏性编辑是产品定位的根本特征，也是本软件区别于普通画图软件的核心；对应里程碑 M2（命令模式 + 组合落地）。

**Independent Test**: 构建一个会话，追加若干调整、撤销若干次、重做若干次，校验每一步的指令栈内容与渲染结果；不依赖故事 1 之外的任何能力。

**Acceptance Scenarios**:

1. **Given** 一个新编辑会话，**When** 依次追加「亮度 1.2」「对比度 1.5」，**Then** 会话包含两条按追加顺序排列的调整记录
2. **Given** 会话已有记录，**When** 追加一条与栈顶同类的调整（如亮度 1.2 后再亮度 1.5），**Then** 两条合并为一条「亮度 1.5」，而非新增一条
3. **Given** 会话含两条记录，**When** 撤销一次，**Then** 仅剩第一条；再重做一次，**Then** 两条全部恢复且顺序不变
4. **Given** 空会话或已全部撤销的会话，**When** 再次撤销或重做，**Then** 引擎报告无可操作项且状态不发生变化
5. **Given** 任意多次调整后，**When** 渲染结果，**Then** 原始图像数据在内存与磁盘上均未被修改

---

### User Story 3 - 多格式图片统一加载 (Priority: P2)

作为上层应用开发者，我把 JPEG、PNG、BMP、WebP 或常见相机 RAW 文件的路径交给引擎，引擎识别格式、解码为统一的内存图像表示并提供多级分辨率预览（缩略图/中等/全图），后续处理对「图从哪来」完全无感。

**Why this priority**: 资产抽象层是开闭原则的扩展点（RAW 支持零修改接入既有管线），但其价值建立在故事 1、2 之上；对应里程碑 M3（继承体系二 + 双工厂）。

**Independent Test**: 对每种支持格式各准备一个样例文件，逐一交给引擎加载并校验解码结果、元数据与预览生成；RAW 解码失败时引擎报告格式化错误而非崩溃。

**Acceptance Scenarios**:

1. **Given** 各一个 JPEG/PNG/BMP/WebP 样例文件，**When** 分别交给引擎加载，**Then** 均得到统一的内存图像表示及尺寸、格式等元数据
2. **Given** 一个 RAW 样例文件，**When** 交给引擎加载，**Then** 解码结果与普通图片走完全相同的后续处理流程（应用同一组调整得到同类结果）
3. **Given** 一张已加载图片，**When** 请求多级预览，**Then** 得到缩略图、中等、全图三级分辨率且画质逐级提升
4. **Given** 引擎不支持的扩展名或损坏文件，**When** 交给引擎加载，**Then** 引擎抛出可识别的格式化错误并给出人类可读的原因，不产生部分加载的残留状态
5. **Given** 一个新的图片格式需求，**When** 仅新增一个资产子类并在工厂注册，**Then** 全部既有代码（调整、会话、渲染、导出）零修改即可处理新格式

---

### User Story 4 - 编辑状态持久化与恢复 (Priority: P2)

作为端到端使用者，我编辑一张图片后关闭程序；重新打开同一图片时，引擎从随图片存放的参数文件恢复全部编辑记录，我的调整不丢失。

**Why this priority**: 「重开不丢失」是需求范围内明确承诺的非破坏性能力闭环；依赖故事 2 的会话与序列化设计。

**Independent Test**: 创建会话、追加调整、保存参数文件、重建会话并加载，比对恢复前后指令栈与渲染结果完全一致。

**Acceptance Scenarios**:

1. **Given** 含若干调整的会话，**When** 保存参数文件，**Then** 生成与图片关联的 JSON 文件，其中每条记录含类型标识与参数，原始图片文件未被写入
2. **Given** 已保存的参数文件，**When** 全新会话加载它，**Then** 指令栈完整重建，渲染结果与保存前一致
3. **Given** 参数文件被手工破坏或类型标识无法识别，**When** 加载，**Then** 引擎报告明确的损坏/未知记录错误，不静默丢弃

---

### User Story 5 - 成品导出、直方图与进度通知 (Priority: P3)

作为端到端使用者，我把编辑完成的图片导出为 JPEG 或 PNG 成品文件；导出与渲染过程中引擎对外通知进度与完成/失败事件，并可输出图片的 RGB 三通道直方图统计供界面绘图消费。

**Why this priority**: 导出是完整工作流「打开 → 编辑 → 导出」的收口；直方图与事件通知服务于后续界面层（M5），对引擎本身属增强能力。

**Independent Test**: 对一个含多条调整的会话执行导出，校验成品文件生成且像素等于按指令链逐条应用的结果；注册回调后触发渲染，校验进度与完成事件按序到达。

**Acceptance Scenarios**:

1. **Given** 含多条调整的会话，**When** 导出为 JPEG/PNG，**Then** 成品文件的像素与「从头按指令链应用全部调整」的结果一致，且可指定输出格式
2. **Given** 导出或预览渲染任务，**When** 注册进度/完成/失败回调后执行，**Then** 事件按「进度 →（完成或失败）」顺序送达，失败时附原因且不产生半成品文件
3. **Given** 一张图片，**When** 请求直方图统计，**Then** 得到 RGB 三通道的分布数据，可直接用于绘制直方图
4. **Given** 一张彩色图片，**When** 应用直方图均衡调整，**Then** 输出图像对比度增强且无可见色偏（仅亮度通道被均衡）

### Edge Cases

- 调整参数在边界值（最小值/最大值/默认值）时：MUST 正常执行且默认参数（值为中性）时输出与原图一致
- 空指令栈的会话：渲染结果 MUST 等于原图
- 极大分辨率图片（如 8000×6000）：加载、预览、导出 MUST 可完成，预览级先行返回不被全图渲染阻塞
- 裁剪框超出图像边界或宽高为 0：MUST 拒绝并报告参数错误
- 旋转到非 90° 倍数角度后画布尺寸变化：MUST 在会话中如实反映新尺寸
- 撤销栈与重做栈在「撤销后追加新调整」时的行为：MUST 清空重做栈（追加使旧重做历史失效）
- RAW 文件来自不支持机型：MUST 抛格式化异常并可被上层捕获提示，进程不崩溃
- 同名参数文件已存在：保存 MUST 覆盖旧文件且不残留临时文件

## Requirements *(mandatory)*

### Functional Requirements

**调整能力**

- **FR-001**: 引擎 MUST 提供 8 类图像调整：亮度、对比度、饱和度、锐度、色温、裁剪、旋转、直方图均衡
- **FR-002**: 每类调整 MUST 声明自己的名称与参数模式（键名、取值范围、默认值），参数模式可供上层校验；所有调整的参数统一采用 0.0–2.0 浮点因子刻度，1.0 为中性值（应用默认参数时输出与原图一致），裁剪/旋转等几何参数除外（按其自然单位定义）
- **FR-003**: 每类调整 MUST 可序列化为「类型标识 + 参数字典」并可由该数据完整重建（往返无损）
- **FR-004**: 每类调整 MUST 定义同类合并规则：两条同类调整合并后，语义等价于后一条单独应用
- **FR-005**: 直方图均衡 MUST 仅作用于亮度通道以保护色彩，禁止对 RGB 三通道分别均衡
- **FR-006**: 引擎 MUST 提供按名称字符串创建任意已注册调整实例的途径，上层不得依赖具体调整类型

**资产能力**

- **FR-007**: 引擎 MUST 支持加载 JPEG、PNG、BMP、WebP 与常见相机 RAW 格式；RAW 支持以 .ARW（索尼）为主验收格式（MUST 验证通过），.CR2/.NEF 等其余格式尽力支持
- **FR-008**: 所有格式解码后 MUST 产生统一的内存图像表示，下游处理与导出对来源格式零感知
- **FR-009**: 引擎 MUST 提供按文件扩展名自动选择资产类型的入口，新增格式仅通过「新增子类 + 注册」接入
- **FR-010**: 引擎 MUST 为已加载图片生成缩略图/中等/全图三级分辨率预览
- **FR-011**: 解码失败 MUST 抛出格式化异常（含文件路径与原因），不得使进程崩溃或留下半初始化对象

**会话与历史**

- **FR-012**: 编辑会话 MUST 以有序列表记录调整指令，且只追加/弹出记录，绝不修改原始像素
- **FR-013**: 引擎 MUST 支持撤销（弹出末条记录）与重做（恢复已撤销记录），操作历史无状态丢失
- **FR-014**: 撤销后追加新调整 MUST 清空重做历史
- **FR-015**: 同类相邻调整在入栈前 MUST 自动合并（后值覆盖语义）

**渲染与导出**

- **FR-016**: 渲染 MUST 按指令栈顺序应用全部调整；空栈渲染结果 MUST 与原图一致
- **FR-017**: 引擎 MUST 维护预览缓存并按「指令栈版本号」判定失效，避免无效重渲染
- **FR-018**: 交互级低分预览的重新渲染 MUST 可在全图渲染之前先行完成并返回（渐进式）
- **FR-019**: 导出 MUST 按指令链对全图渲染并写出 JPEG 或 PNG 成品文件，同时将会话状态持久化为原图关联的参数文件（命名遵循 FR-021：`photo.jpg` → `photo.json`）；成品文件自身不生成 Sidecar
- **FR-020**: 导出失败 MUST 不产生半成品文件

**持久化**

- **FR-021**: 会话 MUST 可保存为与图片关联的参数文件（JSON：指令数组 + 图片路径 + 版本号），命名规则为同主名换扩展名（`photo.jpg` → `photo.json`，对应 XMP Sidecar 惯例），原图文件永不写入
- **FR-022**: 加载参数文件时 MUST 按类型标识重建调整实例并注入参数；文件损坏或含未知类型 MUST 报明确错误

**观测与通知**

- **FR-023**: 引擎 MUST 提供直方图统计能力：输出 RGB 三通道分布数据供外部绘图
- **FR-024**: 引擎 MUST 通过窄回调接口对外通知渲染完成、进度、错误三类事件；引擎不得反向依赖任何上层模块

**架构红线（承自准则）**

- **FR-025**: 引擎层 MUST 在全部运行、测试场景中不依赖任何界面框架（可在无浏览器命令行环境完成所有验证）
- **FR-026**: 新增一类调整或一种图片格式 MUST 仅需新增子类与工厂注册，存量代码零修改（M6 答辩验收项）

### Key Entities *(include if feature involves data)*

- **调整指令（Adjustment）**: 一次图像调整的抽象；含名称、参数模式、执行、序列化、合并能力；具体类型覆盖 8 类算法
- **图像资产（ImageAsset）**: 一张被编辑的图；含路径、格式、元数据；能解码为统一内存表示并生成多级预览；具体类型按文件格式划分
- **编辑会话（EditSession）**: 一张图的全部编辑记录；有序指令列表 + 撤销/重做历史；是持久化的单位
- **参数文件（Sidecar）**: 会话的持久化形态；与图片同名关联，含指令数组、图片路径、版本号
- **渲染管线（Pipeline）**: 组合资产、会话、预览缓存，负责「原图 → 指令链 → 预览/成品」的全流程调度
- **导出器（Exporter）**: 消费渲染结果写出成品文件与参数文件
- **回调协议（Events）**: 引擎对外的唯一通知出口（进度/完成/错误）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在无浏览器、无界面框架安装的纯净命令行环境中，可完成「加载 → 调整 → 撤销/重做 → 保存/恢复 → 导出」全流程验证，全程零失败
- **SC-002**: 对 8 类调整逐一执行「应用 → 序列化 → 重建 → 再应用」往返，输出图像像素 100% 一致
- **SC-003**: 撤销/重做任意操作序列后，指令栈状态与预期模型 100% 一致（含合并、清空重做等边界）
- **SC-004**: JPEG/PNG/BMP/WebP/RAW 五种格式走同一处理管线，各格式应用相同调整后输出结果与直接处理结果一致
- **SC-005**: 交互级低分预览在全图渲染完成前先行可用（低分先行，全图随后替换），滑块连续调整场景无全图级阻塞；验收只判定顺序性与阻塞缺失，不设硬性时间指标
- **SC-006**: 新增一个演示用调整插件（如「暗角」），仅新增子类与注册，存量代码改动数为 0
- **SC-007**: 引擎层全部自动化单元测试在命令行环境一次通过（全绿），且不依赖网络与浏览器

## Assumptions

- RAW 支持以解码库可处理的常见机型为准；不支持的机型按格式化异常路径处理（设计文档第 9 章风险预案）
- 参数文件采用「类型标识 + 参数字典」的 JSON 协议，对应 Lightroom XMP Sidecar 理念；不需要与真实 XMP 格式互通
- 直方图均衡的「无可见色偏」以仅亮度通道均衡 + 噪声抑制系数为技术保障，验收以人眼比对与通道数据双重确认
- 本特性不包含任何界面层代码；界面集成属后续特性（里程碑 M4–M5）
- 预览缓存的三级分辨率具体像素值（如 240p 级交互预览）由实现阶段按性能实测确定，规格只约束「三级 + 低分先行」
- 测试样例图（含 RAW 样片）由项目自备，答辩演示使用已验证过的样片
