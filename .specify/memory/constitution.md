# PyLightroom Constitution

本项目为面向对象程序设计课程作业「简化版 Adobe Lightroom 桌面级 Web 应用（PyLightroom）」。本准则自技术设计文档（`docs/PyLightroom技术设计文档.md`）提炼而来，是所有规格、计划与实现工作的最高约束，任何 `speckit.specify / plan / tasks / implement` 产出均不得违背。

## Core Principles

### I. UI 与逻辑严格分离（不可协商）

系统严格划分为表现层（`ui/`）、桥接层（`state/`）、核心引擎层（`core/`）三层，依赖方向单向向下。

- `core/` 目录 MUST 零 Reflex 依赖：不出现任何 `import reflex` 语句。此为验收红线，以 grep 断言在 CI/验收环节强制把关，违反即返工。
- 只有 `state/` 层被允许同时 import Reflex 与核心引擎；桥接层单个事件处理器只做「参数转换 + 引擎调用 + 状态回写」三个动作，出现任何业务 if/else 分支即视为逻辑下沉失败，MUST 移入引擎层。
- 层间只传递原始数据与消息对象（参数字典、图像字节、进度事件），禁止传递 UI 组件或框架对象。
- 引擎若需通知外部（渲染完成、进度、错误），MUST 经回调协议（`events.py`，观察者模式）由桥接层注入实现，引擎绝不得反向依赖 UI。

理由：这是「UI 类与逻辑类不耦合」的结构性保障，也是课程考核「UI 与逻辑分离」的直接证据。

### II. 继承立抽象，组合建运行

继承只用于建立抽象分类体系（is-a），组合用于搭建运行期能力（has-a），禁止为炫技而滥用继承。

- 继承集中在两棵抽象族谱：`BaseAdjustment`（8 个调整策略子类，每种算法内聚于单一策略类）与 `BaseImageAsset`（Jpeg/Png/Raw 等资产子类），外加 Reflex `rx.State` 业务子状态。
- 抽象基类只定义契约（抽象方法 `apply` / `load`、模板方法 `serialize`、虚方法 `merge`），不绑定实现。
- 全部运行期结构（`EditSession`、`ImageProcessor`、Undo/Redo 栈、`Exporter`、`SidecarFile`、UI 组件树）MUST 以组合方式搭建。
- 多态调度是消费抽象的方式：指令栈遍历时统一调用 `apply()`，会话对具体指令类型零感知；所有子类 MUST 满足里氏替换，可无差别替换进指令栈与处理器。

### III. 非破坏性编辑契约（不可协商）

原始像素永不修改，这是一切编辑行为的根本约束。

- 用户的每一次调整（滑块、裁剪、旋转）只 MUST 记录为参数指令对象追加进 `EditSession` 指令栈，渲染时顺序应用。
- 导出时才按指令链实时渲染生成新文件；原图文件永不写入，Sidecar（JSON）只存指令序列。
- 撤销/重做基于指令栈操作（弹出/重压），同一滑块连续拖动的指令 MUST 经 `merge` 合并，保证历史粒度干净。

理由：非破坏性是 Lightroom 工作流的灵魂，也是本软件区别于普通画图软件的根本特征。

### IV. 开闭原则：以子类扩展，不动存量

新增调整工具或图片格式 MUST 通过「新增子类 + 工厂注册」完成，存量代码零修改。

- 新调整策略继承 `BaseAdjustment` 并经 `AdjustmentFactory` 注册；新图片格式继承 `BaseImageAsset` 并经 `AssetFactory` 按扩展名分发。
- 上层代码只依赖抽象基类与工厂，禁止直接 import 具体策略/资产子类（工厂与桥接层内部注册处除外）。
- 验收标准（M6）：答辩现场新增一个自定义调整插件，不修改任何旧代码即可工作。

### V. 引擎独立可测，测试先行

核心引擎层 MUST 能在无浏览器的命令行环境独立运行、独立测试、独立复用。

- `core/` 的单元测试（pytest）不依赖 Reflex、浏览器或网络，`ui/` 层的改动永远不需要改引擎的测试。
- 每个里程碑的引擎交付物（M1–M3）MUST 先于对应 UI 集成（M4）通过测试；关键算法（直方图均衡的色偏抑制、撤销合并、序列化往返）MUST 有针对性测试用例。
- 开发顺序即架构证明：逻辑层先于 UI 独立成型并测试，是「UI 与逻辑分离」的过程性证据。

## 技术栈与架构约束

以下选型为项目锁定约束，变更须走准则修订流程：

| 类别 | 选型 | 用途 |
| ---- | ---- | ---- |
| 前端框架 | Reflex | 纯 Python 全栈框架，State 驱动 UI，WebSocket 双向通信 |
| 基础图像处理 | Pillow | I/O、几何变换、ImageEnhance 系列（亮度/对比度/饱和度/锐度） |
| 高级图像处理 | OpenCV | 色温、直方图计算与 CLAHE 均衡（仅亮度通道，防色偏） |
| RAW 解码 | rawpy | 将 RAW 解码为 RGB 矩阵后进入统一处理管线 |
| 数据交换 | JSON | 指令序列化（Sidecar 文件，「类型标识 + 参数字典」协议） |
| 测试 | pytest | 引擎层单元测试 |

补充约束：

- 目录结构即架构：`pylightroom/core|state|ui` 三个物理目录对应三个逻辑层，不得混层放置模块。
- 彩色图直方图均衡 MUST 执行「转 YCrCb/LAB → 仅亮度通道 CLAHE → 转回」流程，禁止对 RGB 三通道分别均衡。
- 依赖版本锁定在 requirements 中；桥接层保持极薄以隔离 Reflex API 变动风险。
- 功能裁剪顺序固定：先弃直方图、再弃色温；OOP 架构（评分主体）在任何裁剪下 MUST 完整保留。

## 开发工作流与质量门

- 里程碑顺序固定：M1 引擎骨架 → M2 会话与历史 → M3 资产与 RAW → M4 Reflex 集成 → M5 完善 → M6 收尾。引擎层（M1–M3）MUST 全部排在接触 Reflex（M4）之前。
- 每个里程碑 MUST 满足设计文档中列明的验收标准方可进入下一阶段（如 M2：撤销重做正确且重开程序状态恢复；M4：grep 断言 core 零 Reflex）。
- 每个 MUST 级约束对应一条可执行检查：grep 断言（分离红线）、pytest 全绿（引擎正确性）、插件演示（开闭原则实证）。
- 风险预案（RAW 解码失败、预览性能、Reflex API 变动、工期超支）按设计文档第 9 章执行，降级方案不得触碰本准则任何原则。

## Governance

- 本准则高于一切其他实践与文档；规格、计划、任务与代码实现与准则冲突时，以准则为准。
- 修订流程：提出修订 → 更新本文档并递增版本号（语义化版本：原则删除/重定义为 MAJOR，新增原则或实质扩展为 MINOR，措辞澄清为 PATCH）→ 在 Sync Impact Report 中记录变更 → 提交前移除该报告。
- 一致性审查：每个里程碑验收与代码评审 MUST 对照第 10 章考核点自查表（继承/组合/多态/抽象/封装/分离/开闭/高内聚低耦合）逐项核对。
- 运行期开发指导使用 Spec Kit 相关模板文件；本文件只承载治理与原则。
